# MDProMod 实施路线图：从单人决斗到 Minecraft 服务器

目标平台：Minecraft Java 1.20.1、Forge 47.4.20、Java 17。

原则：先证明 MDPro3 核心能稳定完成决斗，再接入 Minecraft；每阶段都保存可重复的日志、随机种子、核心/脚本哈希和测试结果。

## 阶段 0：冻结输入并建立基线

- 固定 `ocgcore.dll`、C++ 源码、`script.zip`、`cards.cdb`、公共 Lua 库和禁限表版本。
- 确认 DLL 的 64 位架构、C 接口布局、脚本读取方式和回调生命周期。
- 保留现有源码与资源原样，所有实验输出放在 `D:\MDProMod`。
- 记录当前已知缺口：`Duel.RevealSelectDeckSequence` 缺失、2026 新卡和勘误未完整同步。

验收：已有的 native probe 可重复运行；十张基础卡能够初始化；缺失 API 能被明确记录。

## 阶段 1：单人无界面决斗

先写独立的 headless duel host，不启动 Minecraft。

功能范围：

- 创建一场单人决斗；
- 加载两副固定测试牌组；
- 接收核心选择请求；
- 提交玩家操作；
- 输出公开状态、玩家私有状态和核心消息；
- 正常结束、认输和异常销毁；
- 保存可重放日志。

首批测试：抽卡、通常召唤、攻击、抽卡、死者苏生、灰流丽、连锁、伤害和胜负。

验收：不依赖 Unity 或 Minecraft，可以完整打完一局基础决斗。

## 阶段 2：电脑 AI

先实现简单但可靠的 AI，而不是追求强度：

- 识别可执行的核心选择；
- 基于固定优先级选择发动效果、目标和攻击；
- 支持超时、非法响应和认输；
- 保存 AI 决策日志；
- 支持固定随机种子。

验收：玩家可以稳定与电脑完成完整基础决斗；AI 不会卡死或提交非法响应。

## 阶段 3：Minecraft 单机接入

- Forge 模组启动 headless duel host；
- 添加最小命令，例如创建决斗、加入 AI、认输；
- 决斗场地必须是世界中的实体或方块结构，而不是单独的全屏牌桌；
- 卡组、额外卡组、墓地、除外区和场上卡片必须有对应的实体/方块位置；
- 场上卡片使用独立的卡片实体，保存卡号、实例编号、控制者、区域、序号、表示形式和叠放关系；
- 卡组和额外卡组使用可交互的实体容器，不能允许普通 Minecraft 方式直接拿取其中的卡；
- 手牌显示在玩家物品栏中，但手牌槽必须由模组接管，禁止用普通物品栏规则绕过核心；
- 决斗场地设置阶段按钮，例如抽卡阶段、准备阶段、主要阶段1、战斗阶段、主要阶段2、结束阶段；按钮只提交“请求进入阶段”，最终是否合法由核心决定；
- 先使用卡名、卡号和简单材质验证实体同步，再加入卡图、翻面、动画和粒子；
- 将核心线程与 Minecraft 主线程隔离。

验收：在目标 Forge 47.4.20 环境中，玩家可以从游戏内开始一局并击败 AI。

## Minecraft 世界表现的固定约束

### 决斗场地

每场决斗生成一块独立的实体决斗区域。区域记录决斗 ID、双方位置、朝向、所属世界和所有区域坐标。场地可以先用方块结构生成，之后再替换为专用模型；规则状态不能存储在方块朝向或模型状态中，而应由 duel host 保存。

### 卡片实体

每张实体卡至少需要保存：

- 卡片实例 ID；
- 卡片密码；
- 所属决斗和控制者；
- 当前区域与序号；
- 表侧/里侧表示；
- 攻击表示/守备表示；
- 是否为装备卡或超量素材；
- 可见权限和状态版本。

实体只负责表现和交互。召唤、移动、破坏、翻转、叠放和效果结算都必须先提交给核心，核心返回结果后再更新实体，避免玩家直接拖动物品绕过规则。

### 卡组、额外卡组与手牌

- 卡组和额外卡组表现为世界中的牌堆实体或专用容器，外部玩家只能看到允许公开的信息；
- 墓地和除外区也在场地上有实体位置，便于玩家直接点击查看；
- 决斗开始时临时接管玩家物品栏，把手牌映射到指定槽位；决斗结束、认输或异常恢复后还原决斗前的物品栏快照；
- 客户端可以显示卡名、卡图和数量，但服务端必须持有真实手牌并过滤另一名玩家的视图；
- 手牌卡牌只在决斗期间存在于物品栏，使用不可堆叠的内部卡牌物品，并禁止丢弃、合成、放入箱子或交易；
- 玩家点击手牌时，模组发送核心所需的卡实例选择，而不是把物品从物品栏移动到场地；
- 暂时公开、持续公开和“可以确认对方盖卡”都由服务端权限状态决定，不能只靠客户端隐藏名称。

### 临时物品栏接管

决斗开始前，服务端为每名玩家保存完整物品栏快照，至少包括主物品栏、快捷栏、盔甲栏、副手、游泳/死亡相关状态和当前打开的容器。随后关闭容器并锁定普通物品栏操作，只把手牌写入预留槽位。

决斗期间：

- 玩家不能丢弃、复制、堆叠、合成、交易或通过漏斗转移手牌；
- 普通物品栏点击、快捷键换位、双击整理、容器交互都由服务端拦截；
- 卡牌 ItemStack 只携带决斗实例 ID 和显示信息，真正的卡片位置与状态以 duel host 为准；
- 当卡片被使用、送墓、除外或回到手牌时，服务端按核心结果重写对应槽位；
- 断线时保留决斗状态和物品栏快照，禁止玩家通过重新登录复制或取出卡牌。

决斗结束时按以下顺序恢复：先清除所有决斗卡牌，再关闭可能打开的容器，验证玩家仍在原服务器实例，最后写回快照并发送完整物品栏同步包。若原槽位在决斗期间被外部插件或异常修改，不能静默覆盖；应把冲突物品转入服务器保护缓存并记录日志，避免物品丢失或复制。

快照必须持久化到 D 盘的服务器数据目录，并与决斗 ID、玩家 UUID、世界存档和状态版本关联。服务器崩溃或正常重启后，启动恢复任务扫描未完成的快照，先恢复玩家物品栏，再清理孤立的决斗实体。死亡、传送、切换维度和管理员强制结束决斗都必须走同一套清理流程。

### 阶段按钮

场地按钮应对应核心允许的行动窗口，而不是强制改变阶段。按钮点击后发送 `RequestPhaseAction`，服务端检查当前决斗、当前玩家、当前阶段和核心返回值；不合法时按钮保持原状态并显示核心提示。自动推进阶段、跳过阶段和进入战斗阶段也必须由核心确认。

## 阶段 4：Minecraft 本地联机

- Forge 服务端成为唯一决斗状态持有者；
- 两个客户端只提交玩家选择；
- 服务端分别生成双方的公开信息和私有信息；
- 测试重连、掉线、重复提交和超时；
- 加入手牌公开、一次性确认、查看盖卡权限测试。

验收：同一 Minecraft 服务器内两名玩家可以完成一局决斗，且隐藏信息没有泄露。

## 阶段 5：独立服务器部署

- 将 duel host 与 Forge 服务端打包成可配置组件；
- 决斗房间、日志、回放和崩溃恢复放在 D 盘配置路径；
- 支持多个房间，但每场决斗状态隔离；
- 监控核心进程退出、协议错误和资源泄漏；
- 测试长时间运行和多人并发。

验收：服务器重启后不会破坏 Minecraft 主世界；多个玩家可以同时进行不同决斗。

## 阶段 6：外部 MDPro/YGOPro 房间兼容

仅在前五阶段稳定后进行：

- 先确认目标房间使用的协议和版本；
- 用 headless host 完成加入房间、创建房间、基础操作和结束；
- 比较核心消息、卡库、脚本和禁限表；
- 再把外部房间能力暴露给 Minecraft。

验收：协议版本、卡库和规则完全匹配时，才能宣称可加入外部房间。

## 当前下一步

下一步不是制作 Forge UI，而是实现阶段 1 的最小 headless host，并为它准备固定牌组和回放格式。阶段 1 通过后，再开始阶段 2 的 AI。

## 已根据当前安装包修正的技术基线（2026-10-11）

用户提供的 `D:\MyCardLibrary\mdpro3` 安装包已经证明：阶段 1 不必从旧源码的 Unity 客户端移植开始。应优先以安装包中的新版核心和资源做独立 headless host：

- `MDPro3_Data\Plugins\x86_64\ocgcore.dll`
- `MDPro3_Data\Plugins\x86_64\ygoserver.dll`
- `Data\locales\zh-CN\cards.cdb`
- `Data\script.zip`
- `Data\lflist.conf`

单人 AI 可以先启动本地 `ygoserver.dll`，再启动独立 WindBot TCP 客户端；Minecraft 客户端/服务端只需要实现标准 YGOPro TCP 的必要 CTOS/STOC 和 `GameMessage` 投影。Unity `Assembly-CSharp.dll` 仅作为流程参考，不作为 Forge 运行时依赖。

阶段 1 的最小验证应改为：

1. 复制上述文件到 `D:\MDProMod\runtime\mdpro3-data\`，不修改原安装目录；
2. 用新版核心完成 `create_duel_v2/v2_ex` 或兼容旧接口的 headless smoke test；
3. 启动本地 `ygoserver.dll`，用最小 TCP 客户端完成 JoinGame、UpdateDeck、DuelStart 和基础 Response；
4. 接入一个 `WindBot` 进程，打完固定测试牌组；
5. 记录核心版本、资源哈希、协议包和结束原因。

新版资源已包含持续公开手牌/查看里侧场上卡所需的新常量与脚本引用，但逐卡裁定仍需单独回归。新版 `ClientVersion=4962`，外部房间兼容必须同时匹配协议版本、核心、卡库、脚本和禁限表。
