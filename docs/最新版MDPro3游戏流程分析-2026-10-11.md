# 用户提供的 MDPro3 安装包游戏流程分析

日期：2026-10-11  
安装目录：`D:\MyCardLibrary\mdpro3`  
分析对象：用户提供的当前安装包（文件时间 2026-09-26），不是仅凭本地文件宣称的官网绝对最新版。

## 结论

这份安装包不是一个只能通过 Unity 场景运行的封闭客户端。它由 Unity 前端、原生 `ocgcore.dll`、原生 `ygoserver.dll`、C# WindBot AI 和标准 YGOPro TCP 客户端组成：

- Unity/`Assembly-CSharp.dll` 负责菜单、房间、决斗表现、输入和消息投影；
- `ocgcore.dll` 负责卡片规则、效果、连锁、选择和状态推进；
- `ygoserver.dll` 负责本地或独立的 YGOPro 房间服务器；
- `WindBot` 作为普通 TCP 客户端连接服务器，负责 AI 选择；
- `TcpHelper` 负责连接、收发 CTOS/STOC 数据包；
- `OcgCore`/`DuelMessage` 把 `GameMessage` 解析为卡片、阶段、连锁和选择界面。

因此，Minecraft 模组不应尝试把 Unity 的整个 `Assembly-CSharp.dll` 搬进 Forge。第一版应保留核心与标准协议，把 Minecraft 世界作为状态投影层：核心决定规则，模组将核心状态投影为实体卡、卡组/墓地/除外区、临时手牌物品栏和阶段按钮。

## 启动链

Unity 启动路径可概括为：

```text
MDPro3.exe
  -> MDPro3.Boot.Start
  -> LoadMainSceneAsync
  -> Program.SetRoot
  -> Addressables/资源初始化
  -> Program.Initialize
       -> ResourceManager
       -> BanlistManager
       -> CardImageLoader
       -> OnlineService
       -> 各 Manager/Servant
  -> SceneMain / MainMenu
```

`Program.Update` 每帧先调用 `TcpHelper.PerFrameFunction()`，再更新各个 Manager/Servant。网络接收线程只把数据包放入队列，真正的消息解析和 Unity/状态更新在主线程完成。这一点对 Minecraft 很重要：Forge 主线程不能直接执行 Unity 风格的 UI 或阻塞式核心循环。

## 单人对 AI 的实际调用链

```text
SoloSelector.StartAIForSolo
  -> 读取 bot.conf
  -> 解析 Data/Windbot/Decks/AI_*.ydk
  -> 根据端口、LP、起手、抽卡、禁检查等参数组 ygoserver 参数
  -> YgoServer.StartServer(args)
       -> P/Invoke MDPro3.Net.Dll.start_server
       -> ygoserver.dll 独立线程启动本地服务器
  -> TcpHelper.LinkStart(127.0.0.1, playerName, port, local=true)
       -> Receiver 线程接收 STOC
       -> Sender 线程发送 CTOS
  -> 连接成功回调 StartWindBot
       -> WindBot.Program.Main(args)
       -> Config.Load(args)
       -> DecksManager.Init / NamedCardsManager.InitForMulti
       -> GameClient.Start
       -> 发送 ExternalAddress(23)
       -> 发送 PlayerInfo(16)
       -> 发送 JoinGame(18)
       -> 收到 JoinGame 后发送 UpdateDeck(2)
       -> GameBehavior 处理所有 STOC/GameMessage
       -> GameAI/Executor 产生 Response(1)
```

`StartWindBot` 会把 `Host`、`Port`、`HostInfo`、可选的 `Hand=1` 和 `Dialog` 追加到命令行。AI 不是直接调用核心内部函数，而是像第二个普通玩家一样通过 TCP 连接本地 `ygoserver`。这使得 MC 版可以先复用现成 WindBot 进程，而无需第一天实现完整 AI。

## 远程房间和本地建服

远程联机入口：

```text
OnlineServant.KF_OnlineGame(name, ip, port, password)
  -> TcpHelper.LinkStart(local=false)
  -> TCP 连接服务器
  -> ExternalAddress
  -> PlayerInfo
  -> JoinGame
  -> JoinGame/TypeChange/房间状态
```

本地建服入口：

```text
OnlineServant.CreateServer(serverArgs)
  -> 查找 7911 起的可用端口
  -> YgoServer.StartServer(args)
  -> TcpHelper.LinkStart(127.0.0.1, ... local=true)
```

安装包的 `hosts2.conf` 含有多个标准 YGOPro/MDPro 服务器地址和 Evolution 的 OCG、TCG、Genesys、MD、TCGPRE 等模式。它证明客户端仍保留标准房间入口，但是否能加入某个具体外部房间还取决于服务器协议版本、密码格式、卡库、脚本和禁限表是否匹配。

MyCard 房间发现/账号服务属于额外的 REST/WebSocket 服务。第一版 MC 客户端只需要允许输入地址、端口和 HostInfo 密码；后续再接 MyCard 房间发现 API。

## TCP 协议事实

当前安装包使用标准 YGOPro 风格 TCP：

- 每个包：2 字节 little-endian 长度，随后是 1 字节功能号和 payload；
- `CTOS`：`Response=1`、`UpdateDeck=2`、`HandResult=3`、`TpResult=4`、`PlayerInfo=16`、`JoinGame=18`、`Leave=19`、`Surrender=20`、`TimeConfirm=21`、`Chat=22`、`ExternalAddress=23`、房主/准备操作为 32–37；
- `STOC`：`GameMsg=1`、`Error=2`、`SelectHand=3`、`SelectTp=4`、`HandResult=5`、`TpResult=6`、`CreateGame=17`、`JoinGame=18`、`TypeChange=19`、`DuelStart=21`、`DuelEnd=22`、`Replay=23`、`TimeLimit=24`、房间事件为 32–35；
- `JoinGame` 包含客户端版本、房间标志和固定宽度 UTF-16 密码；
- 当前客户端常量 `ClientVersion=4962`（十六进制 `0x1361`）。

MC 侧可以实现一个小型 `YgoTcpClient`，只处理必要的 CTOS/STOC，不必依赖 Unity 或 `Assembly-CSharp.dll`。

## 房间到决斗的生命周期

```text
连接成功
  -> JoinGame
  -> 读取 LFList / Rule / Mode / MasterRule / NoCheck / NoShuffle / LP / 起手 / 抽卡 / 时间
  -> TypeChange 确认座位和房主状态
  -> UpdateDeck 提交主卡组 + 额外卡组 + 副卡组卡号
  -> Ready / HsStart
  -> DuelStart
  -> GameMsg(Start)
  -> 创建双方卡组/额外卡组/场上投影
  -> 持续接收 GameMsg
  -> 等待需要玩家回答的选择消息
  -> 发送 CTOS Response
  -> 继续接收移动、连锁、战斗、阶段和效果结果
  -> GameMsg(Win) / STOC DuelEnd
  -> 退出决斗、恢复房间或返回菜单
```

房间层 `RoomServant` 负责座位、准备、猜拳、先后手、卡组提交和决斗开始。收到 `DuelStart` 后，客户端切入 `OcgCore` 决斗层；收到 `DuelEnd` 后标记结束并清理连接。

## 核心消息和状态投影

`RoomServant.StocMessage_GameMsg` 将服务器传来的功能号和 payload 包装为 `Package`，送入 `OcgCore.AddPackage`。`OcgCore.ProcessMessage` 再把包交给 `MessageDispatcher` 和 `DuelMessage`：

```text
STOC GameMsg
  -> RoomServant.StocMessage_GameMsg
  -> OcgCore.AddPackage
  -> OcgCore.ProcessMessage
  -> MessageDispatcher
  -> DuelMessage/LogMessage/VoiceMessage
  -> 更新核心投影状态
  -> 如果需要玩家选择，等待交互
  -> SendReturn
  -> RoomServant.Handler
  -> TcpHelper.CtosMessage_Response
```

决斗开始的 `GameMessage.Start` 会读取玩家身份、先后手、规则、双方 LP，并创建卡组/额外卡组占位。卡片移动相关消息包括 `Move`、`Set`、`Flip`、`Equip`、`Overlay`、`Material` 等；客户端用 `GPS(controller, location, sequence, position)` 标识卡片当前区域和表示形式。MC 版应以同样的 GPS/实例状态为唯一来源，世界实体只做投影。

当前客户端会解析完整的选择消息集合：

- `SelectBattleCmd`、`SelectIdleCmd`；
- `SelectEffectYn`、`SelectYesNo`、`SelectOption`；
- `SelectCard`、`SelectChain`、`SelectPlace`、`SelectPosition`；
- `SelectTribute`、`SortChain`、`SelectCounter`、`SelectSum`、`SelectDisfield`；
- `SortCard`、`SelectUnselect`；
- `AnnounceRace`、`AnnounceAttrib`、`AnnounceCard`、`AnnounceNumber`。

Forge 交互不应直接修改实体位置或物品栏，而应把玩家点击转换成当前选择消息需要的 response bytes。服务器收到核心结果后，再更新实体和物品栏。

## 阶段按钮的实现方式

最新版客户端已经有一个 `PhaseButtonHandler`，但按钮本身不推进规则。它只在核心发出 `SelectIdleCmd` 或 `SelectBattleCmd` 并确认存在合法阶段选择时开放：

- `battlePhase`：允许请求进入战斗阶段；
- `main2Phase`：允许请求进入主要阶段 2；
- `endPhase`：允许请求结束阶段。

点击后打开 `PopupDuelPhase`，发送标准 response：

- Battle：整数 `6`；
- Main2：整数 `2`；
- End：根据当前选择上下文发送整数 `3` 或 `7`。

因此 MC 的世界按钮应遵循同一原则：只有核心报告合法选择时才显示/启用；点击只发送阶段选择 response；不允许模组自行把 `Main1` 改成 `Battle`。

## AI 的复用价值

WindBot 使用标准客户端方式工作：

```text
WindBot.Program.Main
  -> Config.Load
  -> 读取卡库/脚本/AI 牌组
  -> GameClient 连接 TCP
  -> GameBehavior 注册 STOC/GameMessage 处理器
  -> GameAI 调用 Executor
  -> 发送 Response
```

AI 牌组脚本位于反编译后的 `WindBot.Game.AI.Decks`，牌组文件位于 `Data/Windbot/Decks`。Minecraft 服务器可以先启动一个独立 WindBot 进程，将其连接到同一个 duel host。这样阶段 2 只需处理进程生命周期、AI 日志和掉线恢复。

## 与旧源码版本的差异

| 项目 | 旧源码 | 用户提供的安装包 |
|---|---:|---:|
| 版本基线 | `Version.txt=1.2.4` | 文件时间 2026-09-26 |
| `lflist` | 主要停留在 2024.10 | 首行含 OCG 2026.10、TCG 2026.5 |
| `cards.cdb` 记录 | 约 13,631 | 约 15,019 |
| `script.zip` 卡片脚本 | 约 12,498 | 约 13,572 |
| `ocgcore.dll` | 旧导出和旧规则能力 | 新增 `create_duel_v2/v2_ex`、查询字段、registry、new card/tag card 等导出 |
| 新卡/规则常量 | 缺少部分新机制 | `EFFECT_REVEAL_ONFIELD=376` 等新常量，脚本含 5 个 `RevealSelectDeckSequence` 引用 |
| AI | 旧源码可见部分 AI | 安装包带完整 WindBot C# 客户端和大量 AI 牌组 |
| 协议 | 标准 YGOPro | 仍为标准 YGOPro TCP，`ClientVersion=4962` |

新的 `EFFECT_REVEAL_ONFIELD` 与脚本引用说明，当前核心已经为“持续公开手牌/查看里侧场上卡”等新卡机制预留了能力；这不能替代逐卡裁定审核，但比旧源码基础更适合作为模组规则基线。

## 对 Minecraft 模组架构的直接影响

建议保留四层：

1. **Forge 表现层**：场地结构、实体卡、卡组/墓地/除外区、阶段按钮、手牌物品栏映射。
2. **Duel host**：服务端权威地管理房间、核心线程、消息队列、玩家权限、超时和恢复。
3. **规则层**：优先调用新版 `ocgcore.dll`；以 `cards.cdb`、`script.zip`、`lflist.conf` 作为同一版本资源集。
4. **AI/网络适配层**：本地 AI 先用 WindBot；外部房间使用标准 YGOPro TCP 客户端。

实体和物品栏必须是核心结果的投影：

- 卡片实体保存决斗 ID、实例 ID、密码、controller、location、sequence、position、叠放/装备关系和可见权限；
- 手牌在决斗开始时保存完整物品栏快照后临时接管；
- 决斗结束、认输、掉线或服务器重启恢复快照；
- 服务器分别生成双方可见状态，避免把对手手牌或里侧卡片信息发到客户端；
- 阶段按钮只提交 response，不能成为第二套规则引擎。

## 推荐验证顺序

1. 用新版 `ocgcore.dll + cards.cdb + script.zip + lflist.conf` 完成 headless 基础决斗；
2. 用本地 `ygoserver.dll` 连接一个独立 WindBot，验证起手、抽卡、召唤、战斗和结束；
3. 实现 MC 单机客户端，只投影一场玩家对 AI 的状态；
4. 在同一 Forge 服务器内验证两名玩家和隐藏信息；
5. 做服务器重启、重连、认输、物品栏恢复和多房间测试；
6. 最后再验证加入外部 MDPro/YGOPro 房间。

外部房间兼容的最低条件是协议版本、核心版本、卡库、脚本和禁限表同时匹配。仅仅能连接 TCP 或看到房间列表，不能证明能够稳定完成一场决斗。
